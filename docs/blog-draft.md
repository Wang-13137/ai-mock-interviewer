# 博客草稿：把毕设重构成 LLM 工程时，我实测推翻的三个「标准做法」

## 开头（定调）

去年我的本科毕设是一个 VR 里的 AI 模拟面试官。答辩完我翻到论文第 39 页，看到自己写的局限性：「不能实时对面试结果进行分析」。今年我把它用 Python + FastAPI 重写了一遍，把那个短板补上了——但这篇文章不讲「我怎么搭的」，讲的是**搭的过程中，三个我以为教科书式的标准做法，被我自己写的评测实测推翻了**。

## 坑一：BM25 的 IDF 在小语料上会变负数

教科书公式 `ln((N-df+0.5)/(df+0.5))` 有个隐含假设：语料足够大。我的题库只有 32 条，一个词出现在超过半数文档里时 IDF 直接变负——于是「问题里包含通用词」反而扣分。Lucene 早就遇到过这件事，所以它的实现是非负变体 `ln(1 + ...)`。

教训：**教科书公式都有适用前提，小样本场景要先验证假设再套用**。这条后来固化成了回归测试。

## 坑二：稠密检索里「搜不到」这件事不存在

BM25 里词不匹配就是 0 分，天然有「无命中」。但向量检索的余弦相似度几乎永远不会是 0——再不相干的文档也有零点几分。如果不设相似度下限，Agent 每次调用检索工具都能「搜到东西」，然后被一堆垃圾召回带偏。

而且这个阈值不能抄：不同 embedding 模型的余弦分布差异极大。我写了个标定脚本在标注集上扫阈值，0.30–0.40 是平台区，0.60 直接崩掉。**阈值是数据分布的函数，不是魔法常数。**

## 坑三：cross-encoder 重排，在我的场景是负收益

「粗排 + cross-encoder 精排」几乎是 RAG 教程的标准结尾。我接了 bge-reranker-base，然后在 60 条手工标注的评测集上实测：

| 配置 | Recall@3 | MRR@10 | Hit@1 |
|---|---|---|---|
| vector | 0.800 | 0.814 | 0.767 |
| vector + 重排 | 0.808 | 0.774 | 0.717 |
| hybrid | 0.825 | 0.829 | 0.800 |
| hybrid + 重排 | 0.825 | 0.767 | 0.700 |

（80 条语料 × 60 条评测，2026-10-16 实跑；原始文件在仓库 reports/。）

Recall@3 基本持平，但**排头两个位置的质量掉了**（MRR 和 Hit@1 双降）——用户只看前三条，
排头变差就是体感变差。原因不难理解：我的文档是短文本（面试问题），bi-encoder 在这个尺度上
已接近天花板，重排器引入的方差大于收益。于是这个 1.1GB 的模型被我默认关闭了，代码留着，
等语料大到粗排开始出错时再开。

**「标配」不等于「适合」，而验证它的成本只是一下午加一个评测脚本。**

## 反转彩蛋：我的结论自己也翻转过一次

更早一版评测集只有 30 条、以字面改写题为主，那时的结论是「纯向量 > 混合检索」。补了 22 条字面零重叠的语义难例后，排序翻转成「混合 > 向量 > BM25」。

也就是说，坑三里的负收益结论、以及正收益结论，**都依赖评测集的构成**。所以评测集本身要防「饱和」（所有方法都满分、看不出差异），字面题和语义题要分组统计。

## 收尾：这套项目真正值钱的不是代码

前面三个坑，本质都是一句话：**教科书和教程给的是「在它假设成立的条件下」的结论，而你的数据不一定满足那些条件**。BM25 假设语料够大、向量检索假设你有相似度下限、cross-encoder 假设你的文档长到值得多花一次推理。我的做法是给每个「标准做法」配一个能证伪它的评测脚本——这比背结论有用。

但比起代码，这个项目里我觉得更值得讲的反而是两件「工程诚实」的事：

**1. 没有 API Key，也能让全链路可测。**
我把 LLM 客户端抽象成一层接口，离线时用一个 EchoClient 替身顶上——它不调任何模型，只回固定的结构化响应。结果是 139 个测试可以完全不依赖网络跑通，从 SSE 流式、Agent 循环、工具注册表到检索层都能测。关键不是「能 mock」，而是**替身和真实客户端的调用契约必须一致**，否则测试过了、上线就炸。

**2. 红线机制：系统要如实交代自己现在跑的是不是替身。**
`/health` 接口会明确报告当前是在接真实模型还是跑替身。这条是我给自己定的硬规矩——**宁可读者知道这是离线模拟，也绝不把替身跑出的数字当成真实模型的指标往外发**。这次写文章时我就卡过一回：有一组时延数字，仓库里的报告写的是「真实调用」，但我后来的治理清单把它划进了替身/mock。两处打架，我选择不发布它，而不是赌哪边对。对外的每一个数字，都得能在原始评测报告里找到、且经得起「这是真跑出来的吗」这一问。

**3. 一致性指标也有「坑」：n 小、类别不均衡时，原始一致率会骗人。**
我做过一轮 LLM-as-judge（生成 glm-4-flash / 裁判 glm-4-air，裁判可解析率 100%），但样本只有 10 条、且和生成同属一家厂商，存在自评偏差，报告当时就自动打了 WARNING。更麻烦的是：评测集类别不均衡时，**原始一致率会虚高**，而 kappa 这类校正指标才诚实——所以我没急着报「裁判和人对齐」，而是把 kappa/QWK 一致性统计一直关着，等凑够 ≥30 条人工打分再开。结论也是这次的真心话：**小样本下，先把「方法对不对」验证清楚，再谈「指标好不好看」**。

如果只能带走一句话：做 LLM 应用，别急着抄「标配」，先给你的每个假设写个能证伪它的脚本——这一下午的评测，比看十篇教程都值钱。
